# 众筹系统软件需求规格说明书（SRS）

## 1. 文档信息

- 项目名称：众筹系统
- 文档名称：Software Requirements Specification
- 文档版本：v1.1-draft
- 编写日期：2026-05-10
- 文档状态：可用于需求评审、技术设计与迭代开发

## 2. 项目概述

### 2.1 背景

本项目建设一个轻量众筹系统，用于公开展示资金池余额、接收用户赞助、展示众筹与支出明细，并为管理员提供赞助管理、退款、支出录入、证据图片维护和条款管理能力。

### 2.2 建设目标

1. 用户可快速查看当前资金池余额与核心统计。
2. 用户可通过微信官方支付 完成赞助支付。
3. 用户提交的昵称和留言需经过腾讯云 TMS 自动审核后再公开展示。
4. 用户可查看支出记录详情、收据截图等证据图片。
5. 管理员可对单笔赞助执行退款，也可在结束众筹后按比例退款所有赞助。
6. 系统应保持公开展示信息、审计信息与支付流水清晰分离。

### 2.3 产品范围

本期范围包含两个子系统：

1. 用户端
2. 管理端

本期不包含以下能力，除非后续版本明确纳入：

1. 多项目并行管理
2. 众筹档位、回报品、物流发货
3. 用户端自主申请退款
4. 多管理员角色分级
5. 自动开票、自动对账、导出报表
6. 原生 App 或多收银台并行支付

## 3. 术语与定义

| 术语 | 定义 |
| --- | --- |
| 赞助/众筹 | 用户完成的一笔资金支持行为，在本 SRS 中同义使用 |
| 众筹记录 | 支付成功后可对外展示的赞助记录，包含展示信息和支付关联信息 |
| 支出记录 | 管理员录入的资金使用记录，包含项目、金额、备注和证据图片 |
| 支出详情 | 支出记录的明细页，包含证据图片、说明和审计可见信息 |
| 证据图片 | 收据截图、转账凭证、票据照片等用于证明支出的图片材料 |
| 资金池 | 当前可展示余额，按赞助净额减支出金额计算 |
| 有效赞助净额 | 某笔赞助的支付成功金额减去已成功退款金额后的剩余金额 |
| 累计赞助总额 | 所有已支付成功赞助的金额总和，不扣减退款 |
| 累计支出总额 | 所有有效支出记录金额总和 |
| 赞助人数 | 发生过至少一笔支付成功的去重用户数 |
| 部分退款 | 对单笔已支付赞助执行小于原支付金额的退款操作 |
| 按比例退款 | 在关闭众筹后，按各笔赞助的有效净额占比分配可退金额 |
| 结束众筹 | 管理员将众筹活动置为关闭，禁止新增赞助，并进入结算或退款流程 |
| 展示信息 | 面向普通用户展示的昵称、留言等内容 |
| 审计信息 | 支付单号、退款单号、操作日志、支付/退款通知、审核记录等不可面向普通用户展示但必须留存的数据 |
| TMS 审核状态 | 腾讯云 TMS 返回的审核结果状态，如待审、通过、拒绝、异常 |

## 5. 业务假设与约束

### 5.1 业务假设

1. 本项目为单一众筹活动，不涉及多项目并行。
2. 用户侧不要求传统注册登录，以会话标识和支付订单关联用户。
3. 首期支付方式固定为 微信官方支付 支付。
4. 昵称与留言属于公开展示信息，不作为财务实名信息。
5. 支出记录允许附带 1 张或多张证据图片，供普通用户查看详情。
6. 已支付资金流水不得直接物理删除，只能通过退款、隐藏展示或审计留痕处理。
7. 金额以人民币计价，内部以“分”为单位存储，展示时转换为“元”并保留两位小数。
8. 结束众筹后，系统应冻结新增赞助入口，并以关闭时刻的快照作为退款分配依据。

### 5.2 外部约束

1. 支付创建、支付结果确认、退款申请和退款结果确认应由 微信官方支付提供能力支持。
2. 支付最终成功与否必须以 微信支付的最终通知或查询结果为准。
3. 腾讯云 TMS 的审核结果必须作为昵称和留言是否可公开展示的依据。
4. 证据图片存储应使用可长期访问、可审计的对象存储或等效能力。
5. 正式环境应保护商户密钥、TMS 密钥、证书和对象存储凭据，不得暴露给普通用户。

## 6. 用户角色

| 角色 | 描述 |
| --- | --- |
| 普通用户 | 访问资金池、众筹记录、支出明细、支出详情并发起赞助 |
| 系统管理员 | 维护赞助记录、退款、支出、证据图片、条款、关停和审计 |
| 微信支付 | 微信官方支付与退款能力提供方 |
| 腾讯云 TMS | 昵称与留言内容审核能力提供方 |

## 7. 功能范围

### 7.1 用户侧功能范围

1. 查看当前资金池余额与辅助统计。
2. 查看众筹记录列表。
3. 查看支出记录列表与详情。
4. 查看收据截图等证据图片。
5. 发起微信官方支付 赞助支付。
6. 查阅当前生效条款与退款说明。
7. 查看众筹是否处于进行中、关闭中或已结束状态。

### 7.2 管理侧功能范围

1. 进行身份认证并访问管理能力。
2. 查看和管理赞助记录。
3. 发起单笔退款并跟踪结果。
4. 结束众筹并发起按比例批量退款。
5. 新增、编辑和维护支出记录及证据图片。
6. 维护条款版本。
7. 查看操作日志、审核记录与外部回调记录。

## 8. 功能需求

### 8.1 用户侧基础展示与访问

#### FR-001 资金池总额展示

1. 系统应在用户访问系统时优先展示当前资金池总额。
2. 资金池总额应显示为人民币格式，例如 `¥ 12,345.67`。
3. 当余额为负数时，系统应直接显示负值，不得强制归零。
4. 资金池总额应基于最新已生效数据计算，不得长期展示过期结果。

#### FR-002 用户侧核心功能可达

1. 系统应支持用户查看公开可见的众筹记录列表。
2. 系统应支持用户查看公开可见的支出记录列表与详情。
3. 系统应支持用户发起赞助流程。
4. 系统应保证上述核心功能可被用户稳定访问。

#### FR-003 列表通用行为

1. 众筹记录与支出记录列表应支持下拉刷新。
2. 列表默认按记录时间倒序排列，最新记录优先显示。
3. 当列表为空时，系统应展示明确的空状态提示。
4. 列表应支持分批加载，且首次加载应在合理时间内返回首批结果。

#### FR-004 辅助统计展示

1. 系统应展示累计赞助总额、累计支出总额、赞助人数等辅助统计。
2. 累计赞助总额应按所有支付成功订单的金额总和计算，不扣减退款。
3. 累计支出总额应按所有有效支出记录金额总和计算。
4. 赞助人数应按支付成功用户的去重用户唯一标识统计。
5. 普通用户与管理员均应可查看上述统计。

#### FR-005 众筹状态展示

1. 系统应向用户展示当前众筹活动状态，例如“进行中”“关闭中”“已结束”。
2. 当众筹已关闭时，赞助入口应明确置灰或禁用，并说明原因。
3. 当众筹处于批量退款阶段时，系统应提示退款正在处理中。

### 8.2 发起赞助与支付

#### FR-010 赞助表单

1. 系统应允许用户填写以下内容：
   - 昵称
   - 金额
   - 留言
   - 政策条款同意勾选
2. 金额为必填项，且必须大于 `0`。
3. 政策条款同意勾选为必选项，未勾选时不得提交支付。
4. 昵称与留言默认为非必填；若昵称为空，系统应直接显示为“匿名用户”。
5. 留言为空时，不影响赞助支付。

#### FR-011 表单校验

1. 系统应校验金额格式，最多保留两位小数。
2. 系统应限制昵称与留言长度，首期约束如下：
   - 昵称：1-20 个可见字符，空值时允许走匿名
   - 留言：0-200 个字符
3. 当字段不合法时，系统应给出明确错误提示。
4. 系统应在提交时再次校验金额、条款勾选标记和文本长度，防止不合法数据进入后续流程。

#### FR-012 条款确认

1. 系统应在赞助表单中提供可点击的政策条款入口。
2. 条款至少应包含：
   - 用户协议
   - 隐私政策
   - 退款说明/资金说明
3. 系统应记录用户提交赞助时勾选同意条款的时间和条款版本。
4. 系统管理员应可在管理端维护条款内容的版本化配置。

#### FR-013 支付发起

1. 用户确认赞助后，系统应先完成昵称和留言的审核，再创建待支付订单。
2. 系统应为每笔赞助生成唯一商户订单号。
3. 系统应使用 微信官方支付 支付接口创建订单，并获得可跳转的 H5 收银地址。
4. 前端应按客户端形态启动支付：小程序调用 `wx.requestPayment`，电脑 Web 展示 Native 二维码，手机 Web 跳转小程序。
5. 系统应在服务端完成签名和验签，不得将商户密钥暴露给客户端。
6. 若用户取消支付，系统应保留订单失败/取消状态，但不得将该笔订单计入众筹记录。

#### FR-014 支付结果确认

1. 系统不得仅依赖用户侧即时返回结果作为支付成功依据。
2. 系统应基于微信支付的最终通知或主动查询结果判定支付状态。
3. 支付成功后，系统应自动生成或激活对应众筹记录，并可在用户侧列表中展示。
4. 支付失败、超时或取消的订单不得进入公开众筹记录。
5. 支付通知和查询结果的处理应保证幂等，重复通知不得重复入账。

#### FR-015 支付状态回显

1. 用户完成支付交互后，系统应优先展示“处理中”状态，直到后端确认最终结果。
2. 若最终结果尚未同步，系统应允许用户刷新订单状态而不是重复创建订单。

### 8.3 内容审核与众筹记录展示

#### FR-020 公开展示信息

1. 众筹记录列表应至少展示：
   - 昵称
   - 金额
   - 留言
   - 记录时间
2. 若管理员清空昵称，系统应展示系统默认名称，例如“匿名用户”。
3. 若管理员清空留言，系统应展示为空或不展示留言内容。

#### FR-021 退款后的展示规则

1. 当某笔赞助发生部分退款时，该记录仍应保留在众筹记录中。
2. 该记录对资金池的贡献额应变为“原支付金额 - 已退款金额”。
3. 系统应支持对部分退款记录增加“部分退款”状态标识。
4. 当某笔赞助已全额退款时，该记录不得再对普通用户公开展示，但应保留在管理员审计查询中。
5. 全额退款记录在用户侧列表中应按不可见处理，而不是仅做状态标记后继续展示。

#### FR-022 TMS 审核流程

1. 用户提交的昵称和留言应接入腾讯云 TMS 自动审核。
2. 只有审核通过的昵称和留言才能公开展示。
3. 若昵称或留言审核拒绝，系统应阻止其进入公开展示状态，并提示用户修改内容或使用匿名/空留言。
4. 管理员修改众筹记录展示昵称或留言后，也应重新进入 TMS 审核流程。
5. 系统应保留审核请求、审核结果、审核时间和拒绝原因摘要。

#### FR-023 审核状态展示

1. 管理员应可查看每条众筹记录的 TMS 审核状态。
2. 管理员应可查看审核失败原因摘要、审核请求标识和最后一次审核时间。
3. 普通用户不得看到 TMS 内部状态码或第三方返回原文。

### 8.4 支出记录展示与详情

#### FR-030 公开展示信息

1. 支出记录列表应至少展示：
   - 支出项目
   - 支出金额
   - 备注
   - 记录时间
2. 支出金额应始终以正数展示，其对资金池的影响在计算层表现为扣减。
3. 支出记录默认按时间倒序展示。

#### FR-031 支出详情查看

1. 用户应可点击任一支出记录进入详情页或详情面板。
2. 支出详情应展示支出项目、金额、备注、创建时间和证据图片。
3. 支出详情应支持查看收据截图、票据照片或其他证据图片的放大预览。
4. 当某条支出没有公开证据图片时，系统应明确显示“暂无公开凭证”。

#### FR-032 证据图片展示规则

1. 一条支出记录应支持绑定一张或多张证据图片。
2. 证据图片应支持排序、预览和单张查看。
3. 管理员可标记某张图片为公开或仅审计可见。
4. 被标记为仅审计可见的图片不得在普通用户详情页展示。

### 8.5 管理员能力：众筹记录、退款与关停

#### FR-040 众筹记录查询

1. 管理员应可查看全部赞助订单及其当前状态。
2. 列表至少应支持按以下条件筛选或搜索：
   - 订单号/退款单号
   - 昵称
   - 支付状态
   - 退款状态
   - TMS 审核状态
   - 时间范围
3. 系统应支持管理员同时查看审计信息与展示信息的对应关系。

#### FR-041 修改昵称与留言

1. 管理员应可修改一条众筹记录的展示昵称。
2. 管理员应可修改一条众筹记录的展示留言。
3. 管理员应可清空昵称和留言。
4. 管理员修改后的内容在 TMS 审核通过前不得覆盖用户侧的最终公开版本。
5. 系统应保存修改人、修改时间、修改前内容、修改后内容和审核结果。

#### FR-042 单笔退款管理

1. 管理员应可对已支付成功的赞助记录发起退款。
2. 系统应支持部分退款与全额退款。
3. 退款金额不得大于该笔订单当前可退余额。
4. 每次退款操作应要求管理员填写退款原因。
5. 系统应保存商户退款单号、支付退款单号、申请金额、退款状态、退款原因、创建时间和完成时间。
6. 退款申请提交成功仅表示支付平台已受理，系统应以支付平台最终确认结果作为退款成功依据。
7. 退款成功后，系统应实时更新该笔众筹记录的有效净额，并重新计算资金池余额。

#### FR-043 结束众筹

1. 管理员应可将众筹活动置为“结束”。
2. 结束后，系统应禁止新的赞助订单创建。
3. 结束操作应记录关闭原因、关闭时间、关闭操作者和快照时间。
4. 关闭后，用户侧赞助入口应明确提示众筹已结束。

#### FR-044 按比例退款所有赞助

1. 管理员在结束众筹后，应可发起“按比例退款所有赞助”的批量结算流程。
2. 系统应以关闭时刻的快照为准，锁定参与分配的赞助订单集合。
3. 批量退款分配应按各笔订单当前有效净额在总有效净额中的占比分摊可退金额。
4. 金额分配应以“分”为单位，使用确定性的舍入规则保证分配总和等于本次可退总额。
5. 批量退款任务应记录每笔退款的成功、失败、重试和最终结论。
6. 批量退款完成后，系统应将众筹活动状态更新为“已结束”或“已结束且已结算”。

#### FR-045 关停后的约束

1. 关停后不得再创建新的赞助订单。
2. 关停后如仍存在未完成的批量退款项，系统应显示“退款处理中”。
3. 关停后管理员不得跳过批量退款流程直接把资金池显示为正常进行中。

### 8.6 管理员能力：支出记录管理

#### FR-050 新增支出记录

1. 管理员应可新增支出记录。
2. 新增支出记录时至少填写：
   - 支出项目
   - 支出金额
   - 备注
3. 支出金额必须大于 `0`。
4. 管理员应可在新增支出时同步上传证据图片。
5. 支出记录创建成功后，应立即参与资金池计算。

#### FR-051 支出记录审计

1. 系统应记录支出记录的创建人、创建时间、最近修改时间和证据图片变更记录。
2. 系统不应物理删除已创建的支出记录，所有变更都应保留审计痕迹。
3. 支出记录被编辑后，系统应保留修改前后的差异信息。

#### FR-052 支出记录编辑

1. 管理员应可编辑支出记录的项目、金额、备注、证据图片和公开状态。
2. 编辑后，系统应立即按最新金额重新计算资金池。
3. 支出记录编辑应写入操作日志，包含修改前后内容和操作者。

#### FR-053 支出详情发布

1. 管理员应可将支出记录设置为公开详情或仅审计可见。
2. 当详情为公开时，用户侧应可点击查看详情与公开证据图片。
3. 当详情为仅审计可见时，普通用户列表仍可见该支出摘要，但不能查看私密图片。

### 8.7 资金池计算

#### FR-060 计算公式

系统应按以下公式计算当前资金池：

```text
资金池余额 = SUM(所有赞助记录的有效赞助净额) - SUM(所有有效支出记录金额)
```

其中：

```text
有效赞助净额 = 支付成功金额 - 已成功退款金额
```

#### FR-061 计算规则

1. 所有金额存储使用“分”。
2. 资金池计算应以系统权威数据为准。
3. 同一笔赞助发生多次部分退款时，应累计已退款金额。
4. 全额退款后，该笔赞助记录的有效赞助净额应为 `0`。
5. 被作废的支出记录不参与资金池计算。
6. 资金池允许为负数。
7. 批量按比例退款应以关闭时刻的快照数据计算，不得混用后续新增或变更数据。

#### FR-062 关闭结算规则

1. 关停前后产生的统计口径应明确区分，避免关闭后继续接受新赞助影响已锁定的分配结果。
2. 批量退款成功的金额应立即从资金池中扣减。
3. 批量退款失败的金额应保留为待重试，不得重复扣减。

### 8.8 操作日志与审计

#### FR-070 操作日志

系统应对以下管理动作生成审计日志：

1. 管理员登录/退出
2. 修改昵称
3. 修改留言
4. 清空昵称或留言
5. 发起单笔退款
6. 发起批量按比例退款
7. 退款结果回写
8. 新增支出记录
9. 支出记录编辑或作废（若启用）
10. 上传、删除或隐藏证据图片
11. 结束众筹

#### FR-071 支付与退款处理一致性

1. 支付结果处理应保证幂等，重复通知不得重复入账。
2. 退款结果处理应保证幂等，重复通知不得重复扣减。
3. 系统应保留关键支付与退款通知的处理记录。
4. 批量按比例退款任务中的每一笔子退款也应支持幂等。

#### FR-072 外部集成留痕

1. 系统应保留 微信支付创建请求、通知回调、订单查询与退款查询的关键摘要。
2. 系统应保留腾讯云 TMS 的审核请求标识、审核结果、错误摘要与重试记录。
3. 系统应在审计中能追溯任意公开昵称、留言和支出证据图片为何时被谁发布。

## 9. 业务流程

### 9.1 用户赞助流程

1. 用户访问系统并查看当前资金池总额和核心统计。
2. 用户发起赞助并填写必要信息。
3. 系统先完成昵称和留言的 TMS 审核。
4. 系统校验信息并创建待支付订单。
5. 系统调用微信支付创建订单，并按客户端形态返回 JSAPI 参数、Native 二维码或小程序跳转入口。
6. 用户完成支付或取消支付。
7. 系统根据 微信支付最终通知或主动查询结果更新订单状态。
8. 支付成功的订单转为公开众筹记录，并更新资金池。

### 9.2 管理员单笔退款流程

1. 管理员进入管理端，检索目标赞助记录。
2. 管理员查看原支付金额、已退款金额和可退余额。
3. 管理员输入本次退款金额和退款原因。
4. 系统校验退款金额不得超过可退余额。
5. 系统向 微信支付发起退款申请。
6. 系统将退款单状态设为“处理中/已受理”。
7. 系统根据 微信支付最终确认结果更新退款状态。
8. 退款成功后，系统同步更新赞助记录净额和资金池余额。

### 9.3 管理员新增支出流程

1. 管理员进入支出记录新增页。
2. 填写项目、金额、备注并上传证据图片。
3. 系统校验信息合法性后创建支出记录。
4. 资金池余额立即更新。
5. 用户侧支出记录列表刷新后可见该记录，详情页可查看公开证据图片。

### 9.4 结束众筹与按比例退款流程

1. 管理员确认关闭原因并执行“结束众筹”。
2. 系统冻结新增赞助入口并生成关闭快照。
3. 管理员发起“按比例退款所有赞助”。
4. 系统按快照数据计算每笔订单的退款分配额。
5. 系统逐笔向微信支付发起子退款并记录结果。
6. 系统汇总成功、失败与待重试项。
7. 所有子退款完成后，系统将活动状态更新为已结束或已结束且已结算。

## 10. 数据需求

### 10.1 赞助订单信息要求

系统对赞助订单至少应记录以下业务信息：

1. 订单标识信息，包括内部主键、商户订单号和支付平台订单号。
2. 支付通道信息，包括微信支付 JSAPI 或 Native 标识、支付启动参数和回调摘要。
3. 用户标识与对外展示信息，包括用户唯一标识、昵称和留言。
4. 审核信息，包括 TMS 审核状态、审核请求标识和审核时间。
5. 金额信息，包括支付金额、已退款累计金额和有效赞助净额。
6. 状态信息，包括订单状态和支付成功时间。
7. 条款信息，包括用户勾选的条款版本和勾选时间。
8. 审计信息，包括创建时间和更新时间。

### 10.2 退款信息要求

系统对退款记录至少应记录以下业务信息：

1. 退款标识信息，包括内部主键、关联赞助订单、商户退款单号和支付退款单号。
2. 金额与原因信息，包括本次退款金额和退款原因。
3. 状态信息，包括退款状态、创建时间和退款成功时间。
4. 审计信息，包括发起管理员及关键处理记录。
5. 批量退款关联信息，包括批次号、分配顺序和快照标识。

### 10.3 支出记录信息要求

系统对支出记录至少应记录以下业务信息：

1. 记录标识信息。
2. 支出项目、支出金额和备注。
3. 当前状态，例如公开或仅审计可见。
4. 审计信息，包括创建管理员、创建时间和更新时间。
5. 公开详情开关和详情页展示摘要。

### 10.4 支出证据图片信息要求

系统对支出证据图片至少应记录以下业务信息：

1. 图片标识信息。
2. 关联支出记录标识。
3. 图片 URL、文件名、排序号和公开状态。
4. 图片说明或标签，例如“收据截图”“转账凭证”。
5. 上传人、上传时间和隐藏/公开变更记录。

### 10.5 文本审核信息要求

系统对 TMS 审核记录至少应记录以下业务信息：

1. 关联业务对象标识，例如赞助记录或编辑请求。
2. 字段类型，例如昵称或留言。
3. 审核请求标识和审核结果。
4. 审核时间、拒绝原因摘要和重试次数。
5. 审核回执或摘要内容，不要求长期保存第三方完整原文。

### 10.6 众筹活动状态信息要求

系统对众筹活动至少应记录以下业务信息：

1. 当前状态，例如进行中、关闭中、退款处理中、已结束。
2. 关闭原因、关闭时间、关闭操作者和关闭快照时间。
3. 批量退款批次号和当前处理进度。
4. 结算完成时间和异常说明。

### 10.7 操作日志信息要求

系统对操作日志至少应记录以下业务信息：

1. 操作人及其角色。
2. 操作类型。
3. 目标对象类型与目标对象标识。
4. 变更前摘要与变更后摘要。
5. 操作时间。

### 10.8 条款版本信息要求

系统对条款版本至少应记录以下业务信息：

1. 版本标识信息，包括内部主键和版本号。
2. 条款标题与正文。
3. 版本状态，例如草稿、生效或停用。
4. 发布时间。
5. 审计信息，包括创建管理员、创建时间和更新时间。

## 11. 状态模型

### 11.1 赞助订单状态

系统至少应区分以下赞助订单业务状态：

1. 待支付
2. 支付中
3. 支付成功
4. 用户取消支付
5. 支付失败
6. 已部分退款
7. 已全额退款
8. 已关闭

### 11.2 退款状态

系统至少应区分以下退款业务状态：

1. 已创建
2. 处理中
3. 退款成功
4. 退款关闭
5. 退款异常

### 11.3 TMS 审核状态

系统至少应区分以下文本审核状态：

1. 待审核
2. 审核通过
3. 审核拒绝
4. 审核异常

### 11.4 众筹活动状态

系统至少应区分以下众筹活动状态：

1. 进行中
2. 关闭中
3. 退款处理中
4. 已结束
5. 已结束且已结算

## 12. 非功能需求

### 12.1 性能

1. 用户首次访问时，应优先获得资金池总额和首批记录。
2. 在正常网络环境下，记录列表首次加载应具备较快响应能力，目标建议为 `P95 <= 2s`。
3. 支付、退款、TMS 审核等关键链路应支持失败重试和异常告警。

### 12.2 可用性

1. 支付成功后的最终入账结果必须可追踪。
2. 当支付最终确认延迟时，系统应避免用户看到重复或冲突状态。
3. 管理员发起退款后，应可看到处理中状态，而非误判为立即成功。
4. TMS 暂时不可用时，系统应明确提示审核失败或待重试，不得直接伪造审核通过结果。

### 12.3 安全

1. 管理端必须要求身份认证。
2. 管理能力必须进行权限校验，普通用户不得访问管理能力。
3. 敏感支付密钥、商户证书、TMS 凭据和对象存储凭据不得暴露给普通用户。
4. 管理操作需具备审计能力。
5. 公开证据图片应避免泄露不必要的敏感字段。

### 12.4 数据一致性

1. 资金池计算必须以系统权威数据为准。
2. 支付与退款事件必须幂等处理。
3. 任一时间点应能从明细数据反推出当前资金池结果。
4. 结束众筹后的批量退款必须使用关闭快照，避免后续数据漂移。

### 12.5 合规

1. 系统若收集昵称、留言、用户标识等信息，应同步维护隐私保护说明。
2. 对外展示的条款内容需与当前生效版本一致。
3. 用户提交的昵称与留言需经过 TMS 审核后再公开展示。

## 13. 集成与一致性要求

### 13.1 用户侧能力支撑

1. 系统应为用户侧提供资金池总额查询、众筹记录查询、支出记录查询、支出详情查询和赞助发起所需业务能力。
2. 用户侧获取的数据应与当前业务状态保持一致。

### 13.2 微信支付能力集成

1. 系统应支持支付创建、支付结果确认、退款申请和退款结果确认。
2. 系统应保存业务订单号与退款单号，确保支付与退款处理可追溯。
3. 系统对用户展示的支付状态应清晰、可理解，且不暴露不必要的底层错误细节。
4. 系统应支持微信支付 JSAPI、Native、通知回调与主动查单并存的确认模式。

### 13.3 腾讯云 TMS 集成

1. 系统应在昵称或留言创建/修改时调用 TMS 做文本审核。
2. 系统应保存审核请求标识、审核结果和拒绝原因摘要。
3. 系统应支持审核失败重试，但不得把未通过审核的内容公开展示。

### 13.4 管理侧能力支撑

1. 系统应为管理员提供赞助记录管理、退款处理、支出记录管理、证据图片管理、关停和条款管理所需业务能力。
2. 管理侧与用户侧必须共享同一套权威资金数据和审计数据。

## 14. 验收标准

### 14.1 用户侧

1. 当用户访问系统时，系统应显示当前资金池总额。
2. 当用户查看众筹记录或支出记录时，系统应显示对应列表。
3. 当用户点击支出记录时，系统应打开详情并展示公开证据图片。
4. 当用户填写合法金额并勾选条款后，系统应允许进入微信官方支付 支付。
5. 当支付最终确认成功时，系统应新增一条众筹记录并更新资金池。
6. 当支付取消或失败时，系统不得新增公开众筹记录。
7. 当众筹已结束时，用户不得继续发起赞助。

### 14.2 管理端

1. 当管理员对一条已支付记录执行部分退款时，系统应在退款成功后减少该记录有效净额并同步更新资金池。
2. 当管理员修改或清空昵称/留言时，系统应在 TMS 审核通过后再对用户侧公开。
3. 当管理员新增或编辑一条支出记录时，系统应立即将其纳入资金池计算。
4. 当管理员结束众筹并发起按比例退款时，系统应按快照规则完成所有赞助的退款分配。
5. 当资金池因支出大于赞助净额而为负数时，系统应正确显示负值。

## 15. 已确认事项

以下事项已由需求方确认并纳入本 SRS：

1. 系统应提供管理员专用管理入口，且仅配置一个系统管理员账号。
2. 全额退款后的众筹记录不对普通用户展示。
3. 支出记录支持编辑。
4. 昵称允许完全匿名，直接显示匿名用户。
5. 昵称与留言需接入腾讯云 TMS 审核服务进行自动合规过滤。
6. 需要展示累计赞助总额、累计支出总额、赞助人数等辅助统计。
7. 需要支持管理员对条款内容做管理端版本化配置。
8. 赞助支付首期接入 微信官方支付 支付。
9. 支出记录支持详情页查看收据截图等证据图片。
10. 支持结束众筹并按比例退款所有赞助。

## 17. 附：关键业务原则

1. 公开展示信息与财务审计信息分离。
2. 支付、退款以系统依据支付平台确认后的最终结果为准，不得仅依据用户侧即时反馈直接入账。
3. 资金池必须可由明细反推，避免“黑盒余额”。
4. 对已支付资金流水禁止直接物理删除，优先采用退款、关停、日志留痕等可审计方式处理。
5. 昵称与留言在公开前必须经过 TMS 审核。
6. 结束众筹后的批量退款必须使用关闭快照和确定性舍入规则。
